# 릴리즈·브랜치 수명·롤백 정책

이 문서는 Bookgolas의 릴리즈 기준점, 버전 브랜치 수명, 롤백 절차를 정의한다.
브랜치는 작업과 유지보수를 위한 가변 포인터로 사용하고, 릴리즈 복구 기준점은
불변 태그와 배포 아티팩트로 보존한다.

이 문서는 저장소에 병합된 시점부터 적용한다. GitHub Ruleset의 실제 적용 범위와
릴리즈 권한은 별도 운영 설정으로 관리하며, 문서와 설정이 다르면 릴리즈를
진행하지 않고 먼저 정합성을 맞춘다.

## 1. 기준 문서

- 활성 버전의 기계 판정 원본: `.byungskerlab/release-lines.json`
- 브랜치와 PR 계약: `AGENTS.md`와 전역 `engineering-team` 브랜치 전략
- 이 문서: 태그, 브랜치 수명, 롤백 및 퇴역 절차

활성 버전 registry에 없는 과거 버전은 정상적인 제품 작업이나 승격의 대상이
아니다. 과거 버전의 소스를 보존해야 할 때는 브랜치를 계속 보호하는 대신
릴리즈 태그와 릴리즈 증거를 보존한다.

## 2. 브랜치 수명

| 브랜치 | 역할 | 기본 수명 |
| --- | --- | --- |
| `main` | 운영 소스와 릴리즈 태그의 기준 | 영구 |
| `dev` | 승인된 변경과 활성 라인 동기화 | 영구 |
| `version/<unit>/<x.y.z>` | 한 delivery unit과 한 버전의 개발 라인 | 해당 버전 활성 기간 |
| `release/<unit>/<x.y.z>` | 동결된 QA·승격 후보 | QA·승격·증거 수집 완료까지 |
| `hotfix/<unit>/<x.y.z>` | 운영 장애·긴급 수정 | 핫픽스 배포와 동기화 완료까지 |
| 작업·검토·통합 브랜치 | 하나의 이슈 또는 한시적 검증 | PR·검증 완료까지 |

다음 조건을 모두 만족하면 `version/*`, `release/*`, `hotfix/*` 브랜치를
로컬과 원격에서 삭제한다.

1. 해당 버전의 배포 또는 종료 결정이 완료되었다.
2. 릴리즈 태그와 정확한 커밋 SHA가 기록되었다.
3. 배포 아티팩트 또는 배포 식별자가 기록되었다.
4. 필요한 `dev`·활성 버전 라인 동기화와 검증이 끝났다.
5. 해당 브랜치를 대상으로 한 열린 PR이나 지원 중인 핫픽스가 없다.

지원 중인 이전 버전에 보안·운영 핫픽스를 제공해야 할 때만 버전 브랜치를
유지한다. 단순히 나중에 롤백할 가능성이 있다는 이유만으로 브랜치를 보존하지
않는다. 종료한 버전에 수정이 다시 필요하면 해당 릴리즈 태그에서 새 핫픽스
브랜치를 만든다.

## 3. 릴리즈 태그

실제 배포가 완료된 버전은 delivery unit별 annotated tag를 만든다.

| Delivery unit | 태그 형식 | 예시 |
| --- | --- | --- |
| Web | `web-v<x.y.z>` | `web-v1.1.0` |
| Mobile | `mobile-v<x.y.z>` | `mobile-v1.0.2` |
| Backend | `backend-v<x.y.z>` | `backend-v1.0.2` |
| Agent API/CLI | `agent_api_cli-v<x.y.z>` | `agent_api_cli-v0.1.0` |

태그는 다음 규칙을 따른다.

- 태그가 가리키는 커밋은 실제로 배포한 커밋 또는 그 커밋과 동일한 불변
  아티팩트의 소스 커밋이어야 한다.
- 태그는 annotated tag로 만들고, 생성 후 이동하거나 삭제하지 않는다.
- GitHub에서 릴리즈 태그를 삭제·강제 갱신할 수 없도록 별도 tag Ruleset을
  적용한다.
- 릴리즈 증거에는 태그, 40자리 커밋 SHA, 릴리즈 PR, 배포 아티팩트 또는
  배포 식별자, 데이터베이스 마이그레이션 상태와 롤백 계획을 함께 기록한다.
- 모든 PR에 태그를 만들지는 않는다. 장기 보존이 필요한 릴리즈와 명시적인
  마일스톤만 태그한다.

태그는 버전 브랜치보다 우선하는 롤백 기준점이다. 현재 저장소에 릴리즈 태그가
없다면 다음 배포부터 이 규칙을 적용하고, 이미 배포된 버전은 확인 가능한
배포 커밋과 아티팩트를 먼저 대조한 뒤 소급 태그를 만든다.

## 4. 롤백 절차

### 애플리케이션 또는 Web 배포 롤백

1. 가장 최근의 정상 배포 아티팩트 식별자를 우선 확인한다.
2. 아티팩트가 없으면 해당 버전의 불변 릴리즈 태그와 커밋 SHA를 확인한다.
3. 같은 커밋 또는 같은 아티팩트를 대상 환경에 재배포한다.
4. 인증, 핵심 사용자 흐름, 로그, 데이터 접근을 확인하고 롤백 증거를 기록한다.

운영 `main`을 과거 커밋으로 reset하거나 force-push하지 않는다. Git 이력을
되돌려야 하는 경우에는 해당 PR의 merge commit을 대상으로 revert PR을 만든다.

### 특정 PR 시점으로 복구

- 병합된 PR은 merge commit SHA가 정확한 기준점이다.
- 여러 PR이 포함된 릴리즈는 최종 배포 태그가 전체 릴리즈 상태를 나타낸다.
- 병합되지 않은 PR의 상태를 장기 보존해야 하면 브랜치를 삭제하기 전에 해당
  head SHA에 별도 마일스톤 태그를 만든다. PR 번호만을 복구 기준점으로 삼지
  않는다.
- 브랜치가 없어도 커밋 SHA로 객체를 참조할 수 있지만, 원격의 영구 보존
  기준으로는 태그를 사용한다.

### 데이터베이스와 외부 상태

Git 태그는 소스 코드만 되돌린다. Supabase 스키마, 데이터, Edge Function의
배포 상태, 환경변수, 외부 서비스 상태는 별도 롤백 대상이다.

- 이전 애플리케이션이 현재 스키마와 함께 동작하는지 먼저 확인한다.
- 마이그레이션은 하위 호환 가능한 단계적 변경을 우선한다.
- 필요한 경우 별도 롤백 SQL 또는 백업 복구 절차를 준비한다.
- Dev 환경에서 검증한 뒤 Production 권한과 증거를 확인하고 실행한다.

## 5. 릴리즈 흐름

1. `release-lines.json`에서 활성 버전과 delivery profile을 확인한다.
2. 승인된 `version/<unit>/<x.y.z>` 라인에서 같은 버전의 작업을 검토한다.
3. 범위를 동결하고 정확한 커밋에서 `release/<unit>/<x.y.z>`를 만든다.
4. QA와 배포 전 검증을 release 커밋 또는 불변 아티팩트에 대해 실행한다.
5. release를 `main`으로 승격하고, 결과 커밋에 릴리즈 태그를 만든다.
6. 태그와 동일한 커밋 또는 아티팩트를 배포하고 증거를 기록한다.
7. `dev`와 필요한 활성 버전 라인에 릴리즈 상태를 동기화한다.
8. 위 브랜치 수명 조건을 만족하면 version/release 브랜치를 퇴역시킨다.

현재 Web은 Admin Web `1.0.2`와 소비자 Web `1.1.0`이 별도 활성 라인이다.
두 라인은 각각 `web-v1.0.2`, `web-v1.1.0` 태그를 사용하며, 한 라인의 태그가
다른 라인의 배포 상태를 대신하지 않는다.

## 6. 버전 라인 퇴역

버전 라인을 닫을 때는 governance PR에서 registry의 상태와 활성 버전 목록을
먼저 갱신한다. 그 다음 릴리즈 증거와 태그가 존재하는지 확인하고, GitHub
Ruleset의 보호 범위에서 종료 라인을 제외한 뒤 원격·로컬 브랜치를 삭제한다.

태그, 릴리즈 기록, 배포 아티팩트, 마이그레이션 및 롤백 증거는 브랜치 삭제와
무관하게 보존한다.
